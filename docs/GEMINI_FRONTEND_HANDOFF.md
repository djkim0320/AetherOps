# AetherOps 프런트엔드 디자인 인수인계서

이 문서는 AetherOps의 프런트엔드를 전면 재설계할 디자이너/프런트엔드 에이전트를 위한 작업 설명서다. 현재 DOM, CSS 클래스, 패널 크기와 컴포넌트 배치는 보존 대상이 아니다. 현재 화면을 기능 인벤토리와 Codex 감성의 참고 자료로만 사용하고, 아래의 제품 목적과 동작 계약을 이해한 뒤 새로운 프런트 구조를 설계한다.

## 1. 한 문장 설명

AetherOps는 사용자가 AI와 자연스럽게 대화하다가, 필요할 때 계획을 세우고, 근거 수집·공학 해석·보고서 작성·검토까지 장시간 수행하도록 만든 Windows 11 전용 로컬 연구 에이전트다.

## 2. 제품의 목적

AetherOps의 핵심은 단순 채팅이 아니라 **대화에서 검증 가능한 연구 결과물로 이동하는 과정**이다.

- 평상시에는 Codex 스타일의 일반 대화 환경이다.
- 사용자가 `/plan`을 실행하면 계획 모드가 시작된다.
- 계획 모드에서는 AI가 사용자의 의도를 확인하기 위해 1~3개의 선택형 질문을 제시한다.
- 답변이 충분하면 최종 계획을 작성한다.
- 사용자가 최종 계획을 승인하거나 `/research`를 실행하면 실제 연구 파이프라인이 시작된다.
- 연구 결과는 보고서, 근거 자료, 공학 해석 결과, 리뷰 판정, 지식그래프로 남는다.
- 사용자는 진행 상황, 승인 대기, 산출물과 출처를 한 화면에서 계속 확인할 수 있어야 한다.

제품이 주어야 하는 감정은 “화려한 AI 데모”가 아니라 **조용하고 신뢰할 수 있는 전문 작업 공간**이다.

## 3. 실행 환경과 기술 구조

- 지원 운영체제: Windows 11 x64
- 데스크톱 셸: Go + WebView2
- 프런트엔드: Preact + TypeScript + Vite
- 스타일: 단일 CSS 디자인 시스템
- 그래프: Cytoscape.js
- 배포: 정적 프런트 자산을 하나의 `aetherops.exe`에 임베드
- 통신: 무작위 loopback 주소의 `/api/v1` JSON API와 SSE
- 대화·모델 실행·ChatGPT 로그인·외부 MCP: Codex App Server
- 연구 상태 머신·SQLite·CAS·스케줄러·RAG·지식그래프·브라우저 감독: Go 코어

이 제품은 브라우저에서 공개되는 웹 서비스가 아니다. 화면은 로컬 WebView2에서 실행되며 네이티브 데스크톱 앱처럼 느껴져야 한다.

## 4. 핵심 연구 파이프라인

실제 연구는 다음 네 단계를 순서대로 거친다.

1. `PLAN`: 연구 범위와 작업 스트림을 구조화한다.
2. `COLLECT`: 최대 3개의 독립 수집 작업이 근거와 계산 결과를 병렬로 모은다.
3. `SYNTHESIZE`: 메인 스레드가 근거를 결합해 보고서를 작성한다.
4. `REVIEW`: 격리된 리뷰어가 보고서의 근거 무결성과 품질을 평가한다.

리뷰를 통과하지 못하면 최대 3회 자동 수정한다. 최종 상태는 성공, 품질 실패, 실패, 취소, 중단, 불확실, 승인 대기 등으로 명확히 구분된다.

UI는 이 파이프라인을 “백엔드 로그”처럼 보여주면 안 된다. 사용자가 지금 무엇이 진행 중인지, 무엇이 끝났는지, 무엇을 확인해야 하는지 빠르게 이해하도록 번역해야 한다.

## 5. 현재 화면의 정보 구조

기본 작업 화면은 현재 Codex 데스크톱 앱에서 영감을 받은 3열 구조다. 전면 재설계 후에도 `프로젝트/세션 탐색 → 대화와 작업 → 연구 감독`이라는 정보 관계는 유지해야 하지만, 열의 폭·접힘·drawer·탭·responsive 동작은 새로 설계해도 된다.

### 왼쪽: 프로젝트와 대화 트리

- 프로젝트를 폴더처럼 표시한다.
- 프로젝트 아래에 여러 개의 대화 세션이 있다.
- 프로젝트와 대화의 생성, 선택, 이름 변경, 삭제를 지원한다.
- 하단에는 고정된 설정 버튼과 코어 연결 상태가 있다.
- 사이드바는 파일 탐색기처럼 빠르게 훑을 수 있어야 한다.

### 가운데: 대화와 연구 작업 공간

- 현재 프로젝트와 대화 제목
- 일반 사용자 메시지와 AetherOps 응답
- 계획 인터뷰 질문과 선택지
- 계획 완료 후 “이 계획으로 연구 시작” 동작
- 실행 중인 연구를 나타내는 작은 activity pill
- 하단 고정형 채팅 composer
- `/` 명령어 메뉴
- 계획 모드 표시
- 모델·추론·속도·컨텍스트 설정
- 컨텍스트 사용량 표시

연구는 채팅을 시작하자마자 자동으로 실행되지 않는다. 반드시 계획 또는 명시적 연구 명령을 거친다.

### 오른쪽: 연구 요약 rail

- 현재 계획과 전체 단계 진행률
- 산출물 요약
- 실시간 연구 활동
- 승인 대기 항목
- 런타임 경고
- 실행 취소·재개·폐기 등의 제어

이 rail은 일반적인 통계 대시보드가 아니다. 현재 대화에서 수행 중인 연구의 **작업 감독 패널**이다.

## 6. 별도 화면

좌측 내비게이션 또는 관련 액션을 통해 다음 화면으로 이동한다.

- `workspace`: 대화와 연구 감독
- `knowledge`: 프로젝트 지식그래프 및 온톨로지
- `tools`: 내부 Skill/MCP 제안 검토와 활성화
- `artifacts`: 보고서·근거·리뷰·공학 결과 열람
- `schedules`: 자동 연구 일정 생성과 관리
- `controls`: 내장 인터넷 브라우저 자동화 제어와 긴급 중지
- `settings`: Codex 로그인, API 키, 런타임 상태, 프로젝트 삭제

새 라우터나 거대한 전역 상태관리 라이브러리를 추가하지 않는다. 현재 앱은 작은 로컬 제품이라는 경계를 유지한다.

## 7. 반드시 보존해야 하는 UX 계약

다음 동작은 디자인 변경 중에도 절대 훼손하면 안 된다.

### 입력 키

- `Enter`: 메시지 전송
- `Shift+Enter`: 줄바꿈
- `Ctrl+Enter`: 진행 중인 연구에 스티어링 메시지 전송
- IME 조합 중인 Enter는 전송하지 않는다.

### 대화와 연구

- 일반 대화는 연구를 자동 시작하지 않는다.
- `/plan`: 대화형 계획 모드 시작
- `/research`: 준비된 계획 또는 명시적 질문으로 연구 시작
- 계획 질문은 1~3개, 각 질문은 2~3개의 상호 배타적 선택지를 가진다.
- 사용자는 각 질문에 직접 입력도 할 수 있다.
- 프로젝트마다 여러 개의 독립된 대화 세션을 가진다.
- 같은 프로젝트 안의 연구 실행은 안전한 FIFO 규칙을 따른다.

### 모델 설정 popover

- 모델 선택
- 슬라이더 형태의 추론 수준 선택
- `기본 / 빠름` 속도 선택
- `기본 / 1M` 컨텍스트 선택
- `1M` 컨텍스트는 `gpt-5.6-sol`에서만 활성화
- 다른 모델을 선택하면 컨텍스트는 기본값으로 복귀
- 1M 프로필은 `model_context_window=1000000`, 자동 압축은 `900000`을 요청
- 서버가 요청값보다 작은 컨텍스트를 반환하면 요청값과 실측값을 구분해서 경고

### 산출물

- 사용자에게 raw 파일명과 내부 kind 값을 주된 이름으로 노출하지 않는다.
- “최종 연구 보고서”, “수집된 근거”, “품질 검토”, “공학 해석 결과”처럼 사람이 이해할 수 있는 이름을 우선한다.
- SHA-256, artifact ID 등은 기술 정보 영역에서만 보조적으로 제공한다.

### 승인과 안전

- 승인 대기 항목은 위험도, 서버, 도구, 명령, 인수 해시와 정확한 인수를 검토할 수 있어야 한다.
- 승인/거절 액션은 명확하고 실수하기 어렵게 배치한다.
- 브라우저 긴급 중지는 항상 빠르게 찾을 수 있어야 한다.
- `uncertain`이나 `interrupted` 상태를 성공처럼 보이게 만들지 않는다.

## 8. 전면 재설계 범위

이번 작업은 부분적인 CSS 정리가 아니다. 다음을 새로 설계할 수 있다.

- 전체 앱 셸과 화면 레이아웃
- 좌측 프로젝트/세션 탐색 방식
- 중앙 대화 transcript와 message 표현
- composer, 명령어 메뉴, 계획 모드, 모델 설정 popover
- 우측 연구 감독 rail의 정보 위계와 상호작용
- Knowledge, Tool Studio, Artifacts, Schedules, Controls, Settings 전 화면
- 디자인 토큰, 타이포그래피, 색상, 간격, 경계, radius, 그림자
- 컴포넌트 경계와 프런트 전용 상태 구조
- 좁은 창에서 sidebar와 rail이 접히거나 drawer로 전환되는 방식
- loading, empty, error, warning, approval, interrupted, uncertain 상태

다음은 보존하지 않아도 된다.

- 기존 CSS 선택자와 클래스 이름
- 기존 JSX의 중첩 구조
- 기존 카드와 패널의 크기 및 위치
- 기존 Unicode 아이콘 표현
- 기존 화면별 시각적 장식
- `main.tsx`에 모여 있는 현재 컴포넌트 배치

단, 제품 기능, API 계약, 연구 상태 의미, 승인 경계와 사용자 입력 동작은 그대로 보존한다. 전면 재설계는 프런트엔드에 대한 권한이지 백엔드 계약을 다시 정의할 권한이 아니다.

## 9. 유지할 디자인 방향

현재 디자인은 Codex 데스크톱 앱의 다음 특성을 가져가려 한다.

- 깊은 중성 계열의 다크 테마
- 얇고 절제된 경계선
- 넓은 중앙 작업 공간
- 화면 하단의 큰 composer
- 작은 상태 pill과 낮은 시각적 소음
- 프로젝트/대화 트리 중심의 좌측 탐색
- 작업 상태와 산출물을 모은 우측 rail
- 카드보다 작업 흐름과 텍스트 위계 중심
- 기능을 설명하는 마케팅 문구보다 실제 작업을 우선

Codex의 픽셀을 그대로 복사할 필요는 없다. AetherOps의 연구·근거·승인·공학 기능을 자연스럽게 수용하는 방향으로 발전시킨다.

## 10. 디자인 개선 목표

### 우선순위 1: 시각적 일관성

- 초기의 푸른색 사이버 스타일과 최근의 중성 Codex 스타일이 CSS에 혼재한다.
- 색상, 경계선, radius, 그림자, 간격, 글자 크기를 디자인 토큰으로 정리한다.
- 한 화면에서 카드가 카드 안에 중첩되는 느낌을 줄인다.
- 상태 색은 의미가 있을 때만 사용한다.

### 우선순위 2: 정보 밀도와 가독성

- 전문 도구답게 밀도는 유지하되 답답하지 않아야 한다.
- 한국어 긴 프로젝트명, 대화명, 연구 제목과 오류 메시지를 안전하게 처리한다.
- 중앙 대화가 항상 주인공이어야 하며 좌우 rail이 과도하게 경쟁하지 않게 한다.
- 진행 중, 승인 필요, 실패, 완료의 위계가 즉시 구분되어야 한다.

### 우선순위 3: composer와 모델 설정

- composer는 전체 화면의 시각적 중심이다.
- 모델 설정 popover는 작지만 정보가 잘 정돈되어야 한다.
- 모델, 추론, 속도, 컨텍스트의 관계가 한 번에 이해되어야 한다.
- 컨텍스트 원형 표시는 모델 선택과 분리된 실제 사용량 표시다.
- `1M 요청`과 `App Server 실측`이 다르면 오해하지 않게 표현한다.

### 우선순위 4: 오른쪽 연구 rail

- 플랜, 산출물, 연구 활동, 승인 대기를 같은 강도로 나열하지 않는다.
- 지금 사용자가 행동해야 하는 항목을 우선한다.
- 진행 중인 단계와 최신 산출물은 짧고 스캔 가능해야 한다.
- 상세 정보는 중앙 화면이나 drawer로 열고 rail 자체는 요약을 유지한다.

### 우선순위 5: 접근성과 데스크톱 완성도

- 키보드 탐색, focus ring, disabled, loading, empty, error 상태를 모두 설계한다.
- 색상만으로 상태를 전달하지 않는다.
- Windows 배율과 고해상도 DPI에서 흐려지거나 겹치지 않게 한다.
- 한국어 IME를 방해하지 않는다.
- 스크롤바는 테마에 자연스럽게 녹아들되 발견 가능성과 조작성을 잃지 않는다.
- 좁은 창에서도 기능이 사라지지 않게 우측 rail과 사이드바의 축소 전략을 마련한다.

## 11. 피해야 할 결과

- 랜딩 페이지 또는 마케팅 사이트처럼 보이는 화면
- 큰 hero 문구와 장식용 그라디언트
- 모든 정보를 둥근 카드 안에 넣는 전형적인 SaaS 대시보드
- 과도한 보라색/파란색 네온 테마
- 이유 없는 애니메이션과 유리 질감
- 기능보다 공간을 많이 차지하는 대형 제목
- 프로젝트와 세션을 단순한 드롭다운 하나로 축소
- 연구 단계를 일반적인 퍼센트 차트로만 표현
- raw JSON, DB ID, 파일명을 기본 사용자 경험으로 노출
- 기존 API, 상태 머신, 승인 규칙을 디자인 편의를 위해 변경
- mock 응답을 정상 동작처럼 사용

## 12. 프런트엔드 코드 구조

주요 파일은 다음과 같다.

| 파일 | 역할 |
| --- | --- |
| `frontend/src/main.tsx` | 앱 셸, 프로젝트/세션 트리, 채팅, 계획, 연구 rail, 설정 및 화면 전환 |
| `frontend/src/styles.css` | 전역 디자인 시스템과 모든 화면 스타일 |
| `frontend/src/KnowledgeView.tsx` | 온톨로지·지식그래프 화면 |
| `frontend/src/ToolStudioView.tsx` | 내부 Skill/MCP 검토와 승인 화면 |
| `frontend/src/LifecycleControls.tsx` | 프로젝트 삭제 및 브라우저 프로필 초기화 |
| `frontend/src/api.ts` | 인증된 loopback API와 SSE 클라이언트 |
| `frontend/src/artifact-presentation.ts` | 내부 산출물을 사용자 친화적 이름으로 변환 |
| `frontend/src/knowledge-graph.ts` | Cytoscape 그래프 어댑터와 검증 |
| `frontend/src/knowledge-api.ts` | 지식 API 호출 |

현재 `main.tsx`와 `styles.css`가 지나치게 크므로 전면 재설계 과정에서 적극적으로 분리한다. 아래는 최소 권장 경계이며 더 나은 구조가 있으면 새로 제안할 수 있다.

- `ProjectSessionSidebar`
- `ChatWorkspace`
- `ChatComposer`
- `ModelSettingsPopover`
- `ResearchSummaryRail`
- `PlanQuestionnaire`
- `ArtifactViewer`

기존 `main.tsx`와 `styles.css`를 대폭 다시 작성해도 된다. 단, 새 프레임워크·라우터·무거운 전역 상태관리 패키지는 도입하지 않는다. Preact hooks와 현재 API 모듈을 기반으로 작고 이해 가능한 프런트 구조를 만든다.

## 13. 수정 가능 범위

주된 수정 대상은 다음이며, 이 범위 안에서는 전면적인 생성·삭제·이동·재작성이 허용된다.

- `frontend/src/**`
- 프런트엔드 테스트
- 필요하면 프런트엔드 전용 정적 자산

`frontend/src/main.tsx`, `frontend/src/styles.css`, `KnowledgeView.tsx`, `ToolStudioView.tsx`를 기존 형태로 유지할 필요가 없다. 기능을 빠뜨리지 않는다면 새 컴포넌트와 스타일 파일로 나누고 기존 파일의 상당 부분을 교체할 수 있다.

Go 코어, SQLite 스키마, 연구 상태 전이, API JSON 모양, 권한 정책을 디자인 작업 때문에 임의 변경하지 않는다. API 변경이 정말 필요하면 먼저 변경 이유와 정확한 필드를 제안하고 별도 승인을 받는다.

새 npm 의존성은 가급적 추가하지 않는다. 현재 핵심 의존성은 Preact와 Cytoscape뿐이다. 아이콘은 기존 문자 기반 표현을 일관되게 정리하거나, 의존성 없이 관리 가능한 작은 내부 아이콘 집합으로 통일한다.

## 14. 서버 데이터와 API에 대한 이해

프런트는 다음 범주의 데이터를 다룬다.

- `/api/v1/status`: 코어 준비 상태, 모델 목록, 런타임 경고, 기본 설정
- `/api/v1/projects`: 프로젝트 목록과 생성
- `/api/v1/projects/:id/sessions`: 프로젝트별 대화 세션
- `/api/v1/sessions/:id/chat`: 일반/계획 대화
- `/api/v1/sessions/:id/runs`: 연구 실행
- `/api/v1/sessions/:id/context-usage`: 실제 컨텍스트 사용량
- `/api/v1/runs/:id`: 실행 상태
- `/api/v1/runs/:id/artifacts`: 산출물
- `/api/v1/approvals`: 승인 대기
- `/api/v1/schedules`: 일정
- `/api/v1/knowledge/**`: 지식그래프와 SPARQL
- `/api/v1/projects/:id/tools`: Tool Studio
- `/api/v1/browser/**`: 브라우저 상태, 수동 전환, 긴급 중지
- `/api/v1/auth/codex/**`: Codex 로그인

SSE 이벤트로 연구 진행과 승인 상태가 갱신된다. 새 디자인에서도 실시간 변화가 안정적으로 반영되어야 하며, 화면 전환 때문에 실행 상태가 유실되면 안 된다.

## 15. 작업 방법

1. 먼저 현재 UI를 실행하고 전체 화면, 좁은 화면, DPI 확대 상태를 관찰한다.
2. 현재 화면에서 제공되는 모든 기능과 상태를 빠짐없이 목록화한다.
3. 새 정보 구조, 화면별 wireframe, component map과 디자인 토큰을 먼저 제안한다.
4. 앱 셸과 반응형 레이아웃을 새로 구현한다.
5. 프로젝트/세션 탐색, transcript, composer와 모델 설정을 새로 구현한다.
6. 계획 질문, 연구 진행, 승인, 산출물의 상태 표현을 새로 구현한다.
7. Knowledge, Tool Studio, Artifacts, Schedules, Controls, Settings를 같은 디자인 시스템으로 재작성한다.
8. 기존 기능과 API 호출이 모두 새 컴포넌트에 연결됐는지 대조한다.
9. 좁은 창, 스크롤, 긴 한국어, 빈 상태, 로딩, 오류, disabled 상태를 검증한다.
10. 기존 테스트와 프로덕션 빌드를 실행한다.
11. 변경 전후 스크린샷, 새 컴포넌트 구조와 남은 문제를 보고한다.

## 16. 검증 명령

저장소 루트는 `D:\AI\AetherOps\AetherOps v2`다.

```powershell
cd "D:\AI\AetherOps\AetherOps v2\frontend"
pnpm test
pnpm build
```

전체 제품 검증이 필요하면:

```powershell
cd "D:\AI\AetherOps\AetherOps v2"
.\tools\dev.ps1 test
.\tools\dev.ps1 build
```

빌드 결과는 `build\aetherops.exe` 하나로 제공한다. `fixed`, `new`, `v2`, 날짜 등의 이름을 붙인 EXE를 추가 생성하지 않는다.

## 17. 완료 조건

- Codex 스타일의 절제된 데스크톱 작업 공간이라는 인상이 유지된다.
- 프로젝트/세션 트리, 중앙 대화, 우측 연구 rail의 역할이 명확하다.
- 일반 대화, 계획 인터뷰, 연구 실행이 시각적으로 구분된다.
- 모델·추론·속도·컨텍스트 설정을 작은 popover 안에서 쉽게 이해하고 조작할 수 있다.
- 산출물과 승인이 사용자 친화적인 이름과 위계로 표시된다.
- 긴 한국어와 Windows DPI에서 겹침과 잘림이 없다.
- 키보드, focus, hover, disabled, loading, empty, error 상태가 완성되어 있다.
- 기능과 API 계약이 유지된다.
- 프런트 테스트와 프로덕션 빌드가 통과한다.
- mock 화면이 아니라 실제 AetherOps loopback API와 WebView2에서 검증된다.

## 18. 최종 요청

현재 프런트엔드 구현은 과감하게 교체해도 된다. **제품의 기능과 Codex 스타일의 차분한 작업 감성은 유지하되, 레이아웃·디자인 시스템·컴포넌트 구조·전체 화면 표현은 새로 설계하여 전문 데스크톱 연구 제품 수준으로 다시 만드는 것**이 목표다.

현재의 3열 화면을 그대로 복제할 필요는 없다. 다만 사용자가 프로젝트와 대화를 탐색하고, 중앙에서 AI와 작업하며, 연구 진행·산출물·승인을 동시에 감독할 수 있다는 핵심 관계는 더 나은 방식으로 반드시 남겨야 한다.

작업 전에는 현재 화면의 문제와 개선 방향을 짧게 요약한다. 작업 후에는 변경한 파일, 시각적 결정, 보존한 UX 계약, 실제 검증 결과, 아직 남은 문제를 구분해 보고한다.
